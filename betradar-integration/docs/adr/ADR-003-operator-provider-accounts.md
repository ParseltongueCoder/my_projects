# ADR-003 — ოპერატორის საკუთარი ანგარიშები feed პროვაიდერებთან

- **სტატუსი:** შეთავაზებულია · 2026-10-21 (დასადასტურებელია ღია კითხვების შემდეგ, §5)
- **წყარო:** docs/12 D49 (live booking-ს ოპერატორი აკეთებს პროვაიდერის ადმინში), Q38: **ოპერატორს Betradar-თან და Genius-თან საკუთარი ანგარიში ექნება** (მფლობელი, 2026-10-21)
- **ცვლის:** docs/04 §3-ის ვარაუდს (ერთი UOF ანგარიში, ერთი AMQP კავშირი პლატფორმაზე) და §8.4-ის reseller ლიცენზიის სცენარს

## 1. კონტექსტი

აქამდე ვვარაუდობდით, რომ პლატფორმას აქვს ერთი Betradar ანგარიში (`bookmaker_id`, token, AMQP vhost `/unifiedfeed/{bookmaker_id}`) და მისი მონაცემები ყველა ოპერატორს მიეწოდება (B2B redistribution). მფლობელის გადაწყვეტილებით, ოპერატორს **საკუთარი კონტრაქტი და ანგარიში** აქვს. ამიტომ:

- მონაცემზე უფლება (entitlement) ოპერატორის ანგარიშზეა დამოკიდებული: რომელი სპორტი / ლიგა / პაკეტი აქვს ნაყიდი, რომელი live ივენთი დაბუქა (D49);
- **booking**-ს ოპერატორი თავად აკეთებს პროვაიდერის ადმინში (Betradar Live Booking Calendar, Genius-ის პორტალი) საკუთარი ანგარიშით. ჩვენი ადმინიდან booking არ ხდება, ჩვენთან მხოლოდ დაბუქული ივენთების live მონაცემი მოდის;
- ზოგ პროვაიდერთან odds შეიძლება **ანგარიშზე იყოს მორგებული** (მაგ. მარჟის პარამეტრები პროვაიდერის მხარეს, ⚠ §5 Q-A), ანუ ერთი მატჩის feed odds ორ ოპერატორზე შეიძლება განსხვავდებოდეს;
- სტრუქტურული მონაცემები (სპორტი, ლიგა, ივენთი, მონაწილე, მარკეტის აღწერა) ერთი და იგივეა: იგივე `sr:match:…` / `sr:competitor:…` URN-ები ყველა ანგარიშზე.

## 3. გადაწყვეტილება (შეთავაზება): ვარიანტი C

1. **`sb.feed_account(id, provider_id, operator_id NULL, name, credentials_ref, environment, is_active)`**: ერთი row თითო ოპერატორის ანგარიშზე (`operator_id NULL` = პლატფორმის ტესტ / სადემონსტრაციო ანგარიში). Credential-ები საიდუმლოებების საცავშია (Feed Ops ინახავს მხოლოდ მითითებას), არა ბაზაში.
2. **Adapter multi-account რეჟიმში:** თითო ანგარიშზე ცალკე AMQP consumer და ცალკე recovery / producer state (`sb.producer_status` იღებს `feed_account_id`-ს). ყველა consumer ერთ canonical მოდელში წერს.
3. **სტრუქტურა გაზიარებულია:** fixture, tournament, competitor, market description URN-ით ერთიანდება (`sb.provider_mapping` უცვლელი). პირველი ანგარიში, რომელიც ჩანაწერს მოიტანს, ქმნის მას, დანარჩენები მხოლოდ ამოწმებენ. სტრუქტურული კონფლიქტი (ერთი URN, სხვადასხვა მონაცემი) ლოგში და Feed Ops-ის ალერტში ჩანს.
4. **Odds და მარკეტის სტატუსი ანგარიშის მიხედვით:** `sb.market` / `sb.outcome` ინახავს **ბაზისურ** მდგომარეობას (პირველი / პრიორიტეტული ანგარიში), ხოლო განსხვავებული ანგარიშის მონაცემი `sb.outcome_account_odds(feed_account_id, outcome_id, odds, active, updated_at)`-ში იწერება მხოლოდ მაშინ, როცა ბაზისურისგან განსხვავდება. `OfferService` ოპერატორის ანგარიშის odds-ს იღებს, თუ ასეთი არსებობს, თორემ ბაზისურს. თუ Q-A აჩვენებს, რომ odds ანგარიშზე არ იცვლება, ეს ფენა საერთოდ არ კეთდება და მხოლოდ სტატუსის / entitlement-ის ფილტრი რჩება.
5. **Entitlement = ოპერატორის ანგარიშზე მოსული მონაცემი:** ოპერატორის ოფერში ჩანს მხოლოდ ის ივენთი / მარკეტი, რომელიც მისმა ანგარიშმა მოიტანა (live-ის შემთხვევაში: რომელიც ოპერატორმა პროვაიდერის ადმინში დაბუქა, D49). `Offer.Core`-ის gate: `entitlement:not_in_account` (live-ის მიზეზი trading view-ში: `live:not_booked`).
6. **Settlement** პროვაიდერისგან ერთნაირია (D16), ამიტომ ერთხელ სრულდება ბაზისურ ანგარიშზე. სხვა ანგარიშის settlement დუბლიკატად ითვლება და მხოლოდ შედარდება (განსხვავება = ალერტი).
7. **Booking** ჩვენს სისტემაში არ ხდება (D49): ოპერატორი პროვაიდერის ადმინში ბუქავს. ჩვენ booking-ის სტატუსს მხოლოდ ვკითხულობთ (ფიქსჩერის მონაცემიდან) და BO-ში read-only ვაჩვენებთ.

## 4. შედეგები

- docs/04 §3 (adapter) ფართოვდება multi-account რეჟიმით; Feed Ops-ს ემატება „Feed accounts“ (სტატუსი, recovery, ლაგი ანგარიშის მიხედვით).
- მონიტორინგი ანგარიშის მიხედვით: AMQP კავშირი, producer down, recovery, msg/s.
- ტესტები: ორი ანგარიში simulator-ში (განსხვავებული entitlement-ით და, სურვილისამებრ, განსხვავებული odds-ით), დედუპლიკაცია, entitlement gate (live: ერთ ანგარიშზე დაბუქული, მეორეზე არა).
- ინფრასტრუქტურა: N კავშირი; Betradar-ის ერთ IP-ზე / token-ზე პარალელური სესიების ლიმიტი გადასამოწმებელია (docs/04 დანართი A.1).
- Reseller ლიცენზიის რისკი (docs/04 §8.4) მცირდება: მონაცემს ოპერატორი იღებს საკუთარი კონტრაქტით, პლატფორმა ტექნიკური პროვაიდერია (⚠ §5 Q-C).

## 5. ღია კითხვები (ADR-ის დადასტურებამდე)

- **Q-A:** Betradar-ის / Genius-ის odds ანგარიშის მიხედვით განსხვავდება (პროვაიდერის მხარეს მარჟის / პაკეტის პარამეტრები)? → განსაზღვრავს §3.4-ის საჭიროებას.
- **Q-B:** თითო ოპერატორს თავისი ანგარიშის ხელშეკრულებაში პლატფორმა „ტექნიკურ პროვაიდერად“ უნდა ჩაიწეროს? (Sportradar / Genius-ის მოთხოვნა)
- **Q-C:** ⚖ ერთ ინფრასტრუქტურაზე რამდენიმე ოპერატორის ანგარიშის მონაცემის დამუშავება (გაზიარებული სტრუქტურა) პროვაიდერების პირობებს ხომ არ ეწინააღმდეგება?
- **Q-D:** ოპერატორი, რომელსაც საკუთარი ანგარიში ჯერ არ აქვს (მაგ. პილოტი), დროებით პლატფორმის ანგარიშით მუშაობს თუ არა?
